# Functional Scope and Relationships

前端图必须先由功能模型推导。先确定用户需要完成或体验的功能点，再根据功能之间的关系、状态和用户使用习惯决定页面、路由、导航、组件和视觉重点。

## 1. 功能点记录

为每个候选功能建立一条记录：

| 字段 | 要回答的问题 |
| --- | --- |
| Function ID / name | 这是一个可被用户理解的能力，还是一个实现细节？ |
| User intent | 用户为什么需要它，成功或体验标准是什么？ |
| Trigger / entry | 从哪里、在什么状态下进入？ |
| Inputs / outputs | 用户提供什么，产品返回什么？未知、失败和部分结果是什么？ |
| Objects / permissions | 作用于哪些对象，谁可以查看、修改或执行？ |
| Frequency / criticality | 高频、低频、关键、可选、不可逆还是可恢复？ |
| Preconditions | 依赖哪些数据、权限、选择或前置功能？ |
| States | idle、loading、empty、partial、success、error、permission、draft、interrupted 等实际状态 |
| Canonical owner | 哪个页面或组件拥有权威入口、校验、反馈和数据写入？ |
| Recovery / continuation | 失败、中断、返回和下一功能如何衔接？ |

功能点不是按钮清单。把“显示一个按钮”“加一个卡片”改写为用户能力和结果；如果无法说明用户结果，先回到任务模型。

## 2. 功能关系图

用节点表示功能，用带语义的边表示关系：

- `requires`：前置条件或数据依赖。
- `sequence`：常见连续路径，但允许回退和跳转时要注明。
- `alternative`：同一目标的不同入口或输入方式。
- `parallel`：可以并行完成或比较。
- `contextual-shortcut`：在另一个页面提供快捷入口，仍指向 canonical owner。
- `shared-state`：共享选择、筛选、草稿、权限或结果。
- `recovery`：失败、撤销、重试、恢复和继续。
- `destructive-impact`：会改变、删除、提交或产生费用的后果关系。

记录关系方向、触发条件、携带的上下文和失败行为。孤立功能、重复 owner、循环依赖、必须同时显示却被拆开的功能，以及可按需出现的功能，都会直接改变页面边界。

## 3. 从关系到前端图

按以下顺序推导，而不是按功能数量机械建页面：

1. 将强 `requires/sequence/shared-state` 聚成任务工作面。
2. 将高频、关键、需要持续参考的功能安排在持久区域。
3. 将低频、局部、可恢复的功能安排为按需容器；将复杂、可分享或需要独立恢复的功能升级为页面。
4. 将 `alternative` 和 `contextual-shortcut` 归并到同一个 canonical owner，避免多套语义。
5. 将 `recovery`、`partial`、`permission` 和 `interrupted` 状态放入相同的功能边界，而不是只设计 happy path。
6. 用真实用户习惯调整顺序：首次理解、熟练扫描、批量重复、中断返回、跨设备和低频回访分别如何使用？

输出前端图：页面/路由、导航层级、每页主功能与辅助功能、页面间边、状态/数据流、功能 owner、组件族和响应式转换。每个页面都要能追溯到功能节点和用户结果；每个功能都要能找到入口、反馈、恢复和下一步。

## 4. 用户习惯模型

不要凭空断言用户心理。对关键功能写出可验证的习惯假设：

- 新手需要先理解什么，熟练用户会跳过什么？
- 用户是连续操作、比较、阅读、创作还是探索？
- 用户多久重复一次，是否会批量处理或中断返回？
- 用户在什么设备、时间压力和风险下使用？
- 用户会依赖哪些记忆线索、筛选、最近位置、草稿、快捷入口或可逆操作？
- 哪些功能必须同时看见，哪些功能可以在需要时展开？

每个假设写出支持证据、反例和验证方式。使用习惯影响功能排序、持久性、默认值、导航和布局；不能只用颜色、动画或装饰表达它。
