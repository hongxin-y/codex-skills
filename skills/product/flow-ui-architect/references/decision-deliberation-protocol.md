# Decision Deliberation Protocol

“多思考几步”在 Skill 中表示可审计的多步决策推演，不要求输出隐藏的思维过程。Agent 必须在每个步骤完成前，先做以下判断并记录结论、证据和取舍。

## 每个决策都走六个检查点

1. **Decision**：当前要决定什么？它会影响哪个用户目标、功能点、页面、组件或实现边界？
2. **Evidence**：有哪些 USER facts、REPO facts、现有行为、内容、标准、用户习惯假设和不确定性？哪些是事实，哪些是推断？
3. **Candidates**：至少列出两个合理候选，或说明为什么只有一个可行候选；候选必须在任务、空间、成本、可访问性和实现约束上有真实差异。
4. **User simulation**：用代表性用户的实际使用习惯推演至少三种时刻：首次使用/熟练使用、正常路径/中断返回、短内容/极端内容或窄屏。对阅读、探索、创作等任务，用该任务真实的成功标准替换“完成一次提交”。
5. **Consequence**：检查当前选择对相邻功能、后续页面、状态、权限、响应式、视觉语法、工程稳定性和恢复路径的连锁影响；主动寻找一个会推翻当前选择的反例。
6. **Decision record**：写出选择、拒绝的候选、理由、置信度、待验证项和验证方式。没有候选、推演、反例和验证记录，不能标记 DONE。

## 推演深度

复杂、共享、不可逆、高频或跨页面决策至少完成三层影响推演：

`当前选择 → 直接用户行为 → 下一个功能/状态 → 跨页面或异常后果`

简单局部决策也要完成一层用户和反例检查，不能用“常见组件”“设计惯例”“已经有代码”代替判断。若候选依赖未知信息，标记 `BLOCKED` 或写带影响范围的假设，不用确定语气掩盖未知。

## 适用对象

该协议覆盖：功能是否存在、功能如何分组、页面/路由、导航、Red Route、输入方式、默认值、信息层级、布局骨架、视觉方向、参考图版本、收缩展开、组件容器、颜色/类型、工程结构、验证范围和修复优先级。每类决策都要回到用户目标和功能关系，不允许只在视觉层“深思熟虑”。
