# 渐进完善与依据

## 固定这轮的修改边界

从最新有效指令确定来源、当前文件、要改什么、暂不改什么。文件名里的版本号和时间不能单独证明它是正确基线。原样复制以来源为准；融合版本以用户指定的主版本为准。

“先给方案”只授权提出方案；“检查是否合理”只授权检查；“只改第二点”不包含第一点及后面的建议。确认过的边界跨轮保留，不在反复检查中扩大任务。

融合时先保留主版本完整且适用的段落，再补另一版本真正新增的内容。不要把两种冲突方案拼成看似完整的成稿，也不要把两个版本的数字拼成第三种口径。冲突影响含义且无明确主次时，保留可继续处理的部分，并提一个具体问题。

## 补充内容的依据

重要新句子应能归入以下来源之一。分类放在工作记录或必要的解释中，不给每句正文添加标签。

- **原文明确说明**：能回到指定来源定位。
- **用户明确选择**：可写为本方案采用的规则，但不能自动写成已经实施或他人已经批准。
- **合理推断**：说明所依赖的事实和假设，保留适当限定。
- **新建议**：按建议呈现，不冒充原文、既定要求或真实历史。
- **尚不清楚**：留占位符或问具体问题，不猜填。

对“这是哪里说的”，定位原始材料而不是自己的上一版总结。OCR、提取文本和搜索匹配用于找到证据，不构成独立佐证；页码、日期、出处不得推定。文字要求“说明依据”不等于必须新增审批、责任矩阵或正式签字。

材料说做了某项检查，不证明某个对象已通过；文件描述了计划，不证明计划已执行。预期收益不同于实测结果。发现无依据的既有句子时，按授权修订或另列问题，不因自己曾写过就视为事实。

## 占位符不是凑完整的工具

只对真正缺失、影响这份文档的信息使用 `[TBD]`；沿用用户已有的其他占位写法也可以。不要因为通用模板里有某个栏目，就给所有文档增加该栏目。面向收件人的简短邮件通常不适合生硬的技术占位符，可以向用户说明缺失信息；若用户明确要带占位符的草稿，照做。

填充要有字段粒度：知道地点、不知道日期，可以填地点并保留日期；不把部分填写算成全部完成。作者、负责人、预算、承诺时间、阈值、批准情况及会议结论尤其不能猜。用户明确暂留的占位符原样保留。

新增必要章节但还没有内容时，标题下可放 `[TBD]`。不要改成“本节后续将补充……”来掩盖未回答的问题。真实的待办、责任或依赖属于内容，可以保留；纯粹编写安排放在文件外。

## 逐步处理，而不是反复重写

根据任务选择这一轮：补已知事实、提出待选内容、落实已确认修改、检查逻辑、最后润色。它们是可选工作方式，不是每次必须走完的阶段；请求已经明确时直接执行。

每次检查带着具体问题：来源够不够？本轮是否越界？摘要和正文是否冲突？措辞是否改变承诺？例子是否真的说明规则？不要靠增加标题、换同义词或扩充管理机制来表现进度。已经清楚、正确且符合范围的内容保持不动。

适当压缩重复内容，但保留例外、限制、反例和不同适用范围。提纲重排后核对交叉引用；编号变化不应让“见第 3 节”指向错误内容。对于有意保留的重复，例如执行摘要与详细说明，重点核对口径一致，而不是一概删除。

## 连续工作与交付

对多版本、长文或需要精确追踪的任务，保存必要的本地上下文：原稿与当前文件、授权范围、保留事项，以及已有的修改计划。不要依赖某次会话记忆，也不要把完整敏感材料写入可被无关任务加载的技能文件。

如用户要求对照表，列出位置、原文、实际替换文本，另列“应该填什么”或依据；解释与引文分栏。原始占位符 ID 保持稳定，新增、部分填充、删除与未填分别统计。不要凭相似度猜配后宣称逐字核对。

保持正文、用户要求维护的对照表和 JSON 一致；旧历史稿不要悄悄覆盖。通过核对并重读上下文后交付当前文件。只说明真正完成的检查，未渲染、未访问或未验证的部分明确限定；不承诺“零幻觉”或“完全正确”。
